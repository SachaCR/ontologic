# Ontologic — conventions for AI coding agents

Guidance for writing code with [`ontologic`](https://ontologic.site), a zero-dependency
TypeScript toolkit for Domain-Driven Design.

Everything imports from the package root:

```typescript
import { DomainEntity, DomainEvent, DomainError, BaseDomainInvariant,
         InMemoryRepository, Result, ok, err, switchGuard } from "ontologic";
```

Full docs: <https://ontologic.site/llms.txt> · Full text: <https://ontologic.site/llms-full.txt>
Tested reference implementation: [`src/examples/order`](https://github.com/SachaCR/ontologic/tree/main/packages/ontologic/src/examples/order)

---

## The one rule that governs everything

**Domain failures are returned. Technical failures are thrown.**

| Situation | Mechanism |
|---|---|
| Business rule says no ("order already paid") | `return err(new SomeDomainError(...))` |
| Database is unreachable, save failed | `throw result.error` |
| Entity state violates an invariant | `CorruptedStateError` is thrown for you — never catch it to convert into a `Result` |
| Concurrent write lost the race | Repository returns `ConcurrentWriteError` in a `Result` — recoverable, so retry in normal control flow |

A `CorruptedStateError` means there is a bug. A `Result` error means the business said no. Do not blur them.

## Where business logic goes

The other decision you make constantly:

> **Invariants attach to a single entity** — what it means for that entity to be
> internally consistent. They live on the entity.
>
> **Business rules coordinate multiple entities, or need a query** — they live in use cases.

The tie-breaker: **can the rule be decided from `this.state` alone?** Yes → entity. No → use case.

| Rule | Goes | Why |
|---|---|---|
| "Due date must be after loan date" | Invariant on `Loan` | One entity's own fields |
| "Cannot pay an order that is not PLACED" | Guard in the entity method | Reads its own state |
| "A lost book cannot be lent" | Use case | Needs the `Book` aggregate |
| "At most three active loans per member" | Use case | Needs a count across rows |
| "Does this entity exist?" | Use case, after `getById` returns `ok(undefined)` | Needs a lookup |
| "Is this a valid ISBN?" | System boundary, above the use case | Input validation, not a domain rule |

Also: **IDs are generated by the entity** in `static create`. **Timestamps are passed in**,
not read inside an entity. **Entities never do I/O.** **Read many aggregates, write one** —
`saveWithEvents` is the only atomic unit.

## File layout

One folder per aggregate. Suffixes are load-bearing — follow them exactly.

```
src/domain/
├── entities/order/
│   ├── order.entity.ts              # State interface + entity class + re-exports its errors
│   ├── events/
│   │   ├── orderPaid.event.ts       # one file per event
│   │   └── orderEvents.ts           # union: export type OrderEvent = OrderPaid | ...
│   ├── errors/
│   │   └── invalidStatusTransition.error.ts
│   ├── invariants/
│   │   └── orderHasAtLeastOneItem.ts
│   └── __tests__/order.entity.test.ts
├── useCases/
│   ├── payOrder.use-case.ts         # exports PayOrderUseCase
│   ├── commands/payOrder.command.ts # exports PayOrderCommand
│   ├── queries/readOrder.query.ts   # exports ReadOrderQuery, for read use cases
│   ├── errors/entityNotFound.error.ts
│   └── __tests__/payOrder.use-case.test.ts
└── order.repository.ts
```

The entity file re-exports its own errors so use cases can import the state type and the
errors from one path.

## Entity

```typescript
export interface OrderState {
  id: string;
  customerId: string;
  status: "DRAFT" | "PLACED" | "PAID";
  items: OrderItem[];
  invoiceId?: string;
}

export class Order extends DomainEntity<OrderState> {
  private constructor(id: string, state: OrderState) {
    super(id, state);
    this.addInvariant(orderHasAtLeastOneItemInvariant);
  }

  // Rehydration. This is the mapper you hand to the repository.
  static fromState(id: string, state: OrderState) {
    return new Order(id, state);
  }

  // Creation. Returns the entity AND the event that records its birth.
  static create(params: { customerId: string; firstItem: OrderItem }): {
    order: Order;
    creationEvent: OrderCreated;
  } {
    const id = randomUUID();
    const creationEvent = new OrderCreated(id, {
      customerId: params.customerId,
      status: "DRAFT",
      items: [params.firstItem],
    });

    return {
      order: new Order(id, { id, ...creationEvent.payload }),
      creationEvent,
    };
  }

  // Behavior: guard first, mutate, return the event.
  pay(params: { invoiceId: string }): Result<OrderPaid, InvalidStatusTransition> {
    if (this.state.status !== "PLACED") {
      return err(
        new InvalidStatusTransition("Cannot pay an order that is not PLACED", {
          currentStatus: this.state.status,
          expectedStatus: "PLACED",
        }),
      );
    }

    this.state.status = "PAID";
    this.state.invoiceId = params.invoiceId;

    return ok(new OrderPaid(this.id(), { status: "PAID", invoiceId: params.invoiceId }));
  }
}
```

Non-negotiables:

- **Private constructor.** Construction goes through `create` or `fromState`.
- **Invariants attached in the constructor**, so they hold on both paths.
- **Behavior methods mutate `this.state` and return the event** wrapped in a `Result`.
  They do not return `void`, and they never do I/O.
- `State` is named `<Entity>State` and carries `id` as a field in addition to the constructor argument.

Reading state: `readState()` (invariant check + deep clone — the default) ·
`unsafeReadState()` (check, no clone) · `unsafeRawState()` (neither). Only reach for the
unsafe ones when a profiler says the clone matters, and never mutate what they return.

## Domain event

```typescript
export interface OrderPaidPayload {
  status: "PAID";
  invoiceId: string;
}

export class OrderPaid extends DomainEvent<"ORDER_PAID", 1, OrderPaidPayload> {
  constructor(entityId: string, payload: OrderPaidPayload) {
    super({ name: "ORDER_PAID", version: 1, entityId, payload });
  }
}
```

Names are `SCREAMING_SNAKE_CASE` and past tense — events are facts, not commands.
The version is a literal number, bumped when the payload shape changes.

**Always add the new event to the union file**, or the repository and listener types
will not know about it:

```typescript
export type OrderEvent = OrderCreated | OrderPaid | OrderItemAdded;
```

## Domain error

```typescript
const NAME = "INVALID_STATUS_TRANSITION";

interface InvalidStatusTransitionContext {
  currentStatus: string;
  expectedStatus: string;
}

export class InvalidStatusTransition extends DomainError<
  typeof NAME,
  InvalidStatusTransitionContext
> {
  constructor(message: string, context: InvalidStatusTransitionContext) {
    super({ message, name: NAME, context });

    Object.setPrototypeOf(this, InvalidStatusTransition.prototype);
  }
}
```

Three things that are easy to get wrong and all matter:

1. **`Object.setPrototypeOf(this, X.prototype)` is required, as the last statement.**
   `DomainError`'s own constructor calls `Object.setPrototypeOf(this, DomainError.prototype)`,
   which clobbers your subclass's prototype. Omit the re-set and
   `new InvalidStatusTransition(...) instanceof InvalidStatusTransition` returns **`false`**
   (verified, not theoretical), while `instanceof DomainError` still returns `true` — so the
   bug hides until something does a narrow `instanceof` check.
2. **`const NAME` + `typeof NAME`**, not an inline string literal. The `name` becomes
   the discriminant you switch on.
3. **Put real data in `context`**, not interpolated into the message. That is what makes
   the failure machine-readable downstream.

## Invariant

```typescript
export const orderHasAtLeastOneItemInvariant = new BaseDomainInvariant<OrderState>(
  "Order Has At Least One Item",
  (state) => state.items.length >= 1,
);
```

One invariant per file, exported as `const <name>Invariant`. Combine with
`.and()` `.or()` `.not()` `.xor()` `.andNot()`. Check manually with
`invariant.complyWith(state).isCompliant` — there is no `isSatisfiedBy`.

Invariants are about **internal consistency of the model**, checked on every state read.
They are not input validation, which belongs at the system boundary.

## Action — `Command` or `Query`

A use case is asked to do something, and that something is an **action**: a `Command` when
it changes state, a `Query` when it only reads. Both mirror `DomainEvent` — a literal name
bound once in the subclass, and a payload that is cloned on the way in and out.

```typescript
export class PayOrderCommand extends Command<
  "PAY_ORDER",
  { id: string; invoiceId: string }
> {
  constructor(payload: { id: string; invoiceId: string }) {
    super({ name: "PAY_ORDER", payload });
  }
}

export class ReadOrderQuery extends Query<"READ_ORDER", { id: string }> {
  constructor(payload: { id: string }) {
    super({ name: "READ_ORDER", payload });
  }
}
```

They are not interchangeable: each holds private fields, so a `Query` is never assignable
where a `Command` is expected, even with an identical payload.

## Use case

A use case is a **class implementing `UseCase<Action, Output, Errors>`**, with its
dependencies as constructor parameters — one per aggregate it touches.

```typescript
export class PayOrderUseCase
  implements UseCase<
    PayOrderCommand,
    OrderState,
    InvalidStatusTransition | EntityNotFound
  >
{
  constructor(private readonly orders: OrderRepository) {}

  async execute(
    command: PayOrderCommand,
  ): Promise<Result<OrderState, InvalidStatusTransition | EntityNotFound>> {
    const { id, invoiceId } = command.payload;

    const resultGetById = await this.orders.getById(id);

    if (resultGetById.isErr()) {
      throw resultGetById.error; // technical failure → throw
    }

    const order = resultGetById.value;

    if (order === undefined) {
      return err(new EntityNotFound("This order does not exist", { entityId: id }));
    }

    const result = order.pay({ invoiceId });

    if (result.isErr()) {
      switch (result.error.name) {
        case "INVALID_STATUS_TRANSITION":
          return err(result.error);
        default:
          switchGuard(result.error.name); // compile error if a case is missed
      }
    }

    const saveResult = await this.orders.saveWithEvents(order, result.value);

    if (saveResult.isErr()) {
      throw saveResult.error;
    }

    return ok(order.readState()); // return state, never the entity
  }
}
```

Note that `getById` returns `ok(undefined)` for a missing entity — absence is a domain
decision for the caller, not an infrastructure error. When several events are produced,
collect them in an array and pass it to `saveWithEvents`.

The `Errors` argument is constrained to `DomainError`, so `Result<T, Error>` does not
compile — `Error` has no `context` property. Name the domain failures, or declare `never`
when there are none.

## Repository

`Repository<Entity, Event>` is an interface, not a base class. Every method returns a
`Result`. For tests and prototyping, extend the built-in in-memory implementation —
note it takes **two** type parameters:

```typescript
export class OrderRepository extends InMemoryRepository<Order, OrderEvent> {
  constructor() {
    super(Order.fromState);
  }
}
```

`InMemoryRepository` does **not** implement optimistic locking; versions stay at `0`.
A production repository reads `entity.version()` to guard the write, returns
`ConcurrentWriteError` in a `Result` when the versions disagree, and calls
`entity.setVersion(n)` after a successful save. Domain code never calls `setVersion`.

## Testing (vitest)

Entity tests use no repository and no mocks — build state with a local helper and call
`fromState`. Use-case tests use a real `InMemoryRepository` subclass, freshly constructed
in `beforeEach`, and no mocks.

```typescript
const result = order.removeItem({ itemId: "item-1" });

expect(result.isErr()).toBe(true);
if (result.isErr()) {
  expect(result.error.name).toBe("ORDER_MUST_HAVE_AT_LEAST_ONE_ITEM");
}
```

Prefer that `isErr()` narrowing idiom over `_unsafeUnwrapErr()`; the underscore-prefixed
unwrap helpers are for tests only and throw on the wrong variant. Assert invariant
violations with `expect(() => entity.readState()).toThrow("Corrupted state detected")`.

## Common mistakes

| Mistake | Correct |
|---|---|
| Omitting `Object.setPrototypeOf` in a `DomainError` subclass | Always include it as the last constructor statement |
| Adding an event class but not to the `<Entity>Event` union | Update the union file too |
| `InMemoryRepository<Order>` | `InMemoryRepository<Order, OrderEvent>` |
| `invariant.isSatisfiedBy(state)` | `invariant.complyWith(state).isCompliant` |
| `graphWorkflow.toTree()` | `graphWorkflow.getGraph().toString(opts)` |
| Returning the entity from a use case | Return `entity.readState()` |
| `Promise<Result<T, Error>>` on a use case | Name the domain errors, or use `never` |
| A `Command` for a use case that only reads | Use a `Query` |
| Passing a plain object to `execute` | Wrap it in the use case's `Command` or `Query` |
| Wrapping `CorruptedStateError` in a `Result` | Let it throw; it signals a bug |
| Throwing a domain failure from an entity method | Return `err(...)` |
| `switch` on `error.name` with no `default: switchGuard(...)` | Add it — that is what makes the switch exhaustive |
| Importing `DomainInvariant` from `"ontologic"` | Not exported. Use `BaseDomainInvariant` |
| Public entity constructor | Private, with `create` / `fromState` factories |

Result has a deliberately minimal API: `ok`, `err`, `isOk()`, `isErr()`, `.value`,
`.error`. There is no `map`, `andThen`, `match`, or `unwrapOr` — do not invent them.
