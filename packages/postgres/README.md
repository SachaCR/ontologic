# @ontologic/pg

Postgres-backed `Repository` adapter for [Ontologic](https://ontologic.site).

Implements the `Repository<Entity, Event>` contract from `@ontologic/ontologic`
on top of [`node-postgres`](https://node-postgres.com/). Entity state is stored
as `JSONB`, domain events are appended to an event log table with sequential
per-entity offsets, and `saveWithEvents` is atomic.

## Intended use: prototyping, not production

This adapter is meant for prototyping, demos, and early-stage projects where
you want a Postgres-backed `Repository` working in minutes without designing
a schema. It stores each entity as a single `JSONB` blob, which is convenient
but has real downsides at scale:

- **No relational queries.** You can't filter, join, or sort on entity fields
  without painful JSON path expressions and ad-hoc indexes.
- **No enforced shape.** The database has no idea what's in `state`. A bug in
  your code can write inconsistent or partial state, and Postgres will happily
  store it.
- **Migrations are your problem.** Changing an entity's shape means rewriting
  every row by hand — there are no columns to `ALTER`.
- **Indexing is awkward.** Expression indexes on JSONB work but are easier to
  get wrong, harder to reason about, and harder to maintain than indexes on
  plain columns.
- **Reporting/analytics suffer.** BI tools, dashboards, and downstream ETL
  jobs all expect proper columns.

For real production workloads, write your own `Repository` implementation that
persists each entity into a properly designed relational table (or set of
tables), with the columns, constraints, foreign keys, and indexes your domain
actually needs. The `Repository<Entity, Event>` interface from
`@ontologic/ontologic` is small on purpose — implementing it against a hand-
crafted schema is a few hundred lines of focused code, and you keep all the
benefits of a real relational database.

Use `@ontologic/pg` to move fast early, then graduate to a bespoke repository
when the shape of your domain has settled.

## Install

```bash
npm install @ontologic/pg @ontologic/ontologic pg
```

`pg` and `@ontologic/ontologic` are peer dependencies.

## Quick start

```ts
import { Pool } from "pg";
import { DomainEntity, DomainEventInterface } from "@ontologic/ontologic";
import { PostgresRepository } from "@ontologic/postgres";

interface UserState {
  id: string;
  name: string;
}

class User extends DomainEntity<UserState> {
  static fromState(id: string, state: UserState): User {
    return new User(id, state);
  }
}

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

const repo = new PostgresRepository<User, DomainEventInterface>({
  pool,
  table: "users",
  mapper: User.fromState,
});

// Create tables (idempotent — safe to run on every startup, or skip it and
// manage the schema with your own migrations).
await repo.migrate();

const result = await repo.saveWithEvents(
  new User("1", { id: "1", name: "Alice" }),
  [
    {
      name: "UserCreated",
      version: 1,
      entityId: "1",
      payload: { name: "Alice" },
    },
  ],
);
```

## Schema

`migrate()` creates two tables:

- `<table>` — one row per entity. Columns: `id text primary key`,
  `state jsonb not null`, `created_at timestamptz`, `updated_at timestamptz`.
- `<table>_events` — append-only event log. Columns: `id uuid primary key`
  (generated by the repository), `entity_id text not null`, `name text not null`,
  `version int not null`, `payload jsonb not null`, `event_offset bigint not null`,
  `created_at timestamptz not null`, with `unique (entity_id, event_offset)`
  and an index on `(entity_id, event_offset)`. `event_offset` is the per-entity
  sequence (starts at 0) and is computed at INSERT time via
  `MAX(event_offset) + 1` under the per-entity advisory lock — the application
  never passes a value.

You can pass `schema` and `eventsTable` to customize names.

## Concurrency

`saveWithEvents` runs in a single transaction and takes a Postgres advisory
transaction lock keyed on the entity id, so concurrent writers append
non-overlapping, sequential offsets without retries.

## `onChanges`

Notifications fire on the same instance only. For cross-process pub/sub, wire
your own `LISTEN`/`NOTIFY` on top.

## Caveats

- Entity state and event payloads are serialized as JSON. `Date`, `Map`, `Set`,
  `bigint` and other non-JSON types lose fidelity. Keep state JSON-safe or map
  it in/out via your `mapper`.
